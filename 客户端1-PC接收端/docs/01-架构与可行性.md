# Huawei VR Glass 有线串流接收端 — 架构与可行性

> 目标：低配 PC（眼镜 USB-C 直插）接收高配 PC 的 ALVR 串流，以 SBS 左右眼立体输出到眼镜，并用 IMU 回传头姿。
> 本文基于完整源码 `HuaweiVRGlass-ALVR`（v20.14.1，778 文件）与作者开发日志逐条核实，不写未经验证的臆测。

## 0. 一句话结论

**可行，但不要按"移植手机 APK 到 Windows"的思路做。** 眼镜插在 PC 上时不是网络设备，而是一块 **3200×1600 的本地 DP 显示器**。所以正确做法是：在低配 PC 上做一个"瘦客户端"——用 ALVR 网络协议收流、在 Windows 侧解码、把左右眼画面 SBS 画到这块本地屏、读眼镜 IMU 回传头姿。本工程就是这个瘦客户端。

---

## 1. 决定方案的物理事实

| 事实 | 证据 | 影响 |
|---|---|---|
| 眼镜只有一个 USB-C，插 PC = 本地 DP 显示器（3200×1600），插手机 = WiFi 串流，**互斥** | 开发日志 `MEMORY.md`：EDID `RTK2560`→`HWV0003`；2026-11-23 真机日志 | 眼镜插低配 PC 时，画面输出走本地显示，不走网络 |
| 这块屏不接受 DXGI 独占全屏（`0x887A0022`），须窗口模式 | `deps/huawei-desktop/README.md` | 渲染输出用边界无框全屏窗口 + 交换链 |
| 6DoF SLAM 是华为私有，不可逆向；当大屏 3DoF 够用 | `MEMORY.md` | 本版回传 3DoF 头姿（只读 IMU 朝向，位置固定原点） |
| 眼镜数据通道含 HID IMU（`VID_12D1&PID_3A09&MI_02`，约 1000 包/s） | `deps/huawei-desktop/src/dm_imu.h` | 头姿从 HID 直读，无需华为私有 SDK |

**拓扑：**

```
┌──────────────┐   ALVR(v20.14.1)   ┌─────────────────────┐   USB-C DP   ┌──────────┐
│  高配 PC      │  UDP发现+TCP控制   │  低配 PC             │  3200×1600   │ VR Glass │
│ ALVR Dashboard│ ────H.264流──────► │ hvr-alvr-win-sink.exe│ ───────────► │  SBS左右眼│
│ + SteamVR    │ ◄────tracking───── │  ├ 网络协议层         │              │  + IMU   │
│ + NVENC/AMF  │                    │  ├ FFmpeg解码         │ ◄──HID IMU───│          │
└──────────────┘                    │  └ D3D11 SBS渲染      │              └──────────┘
                                    └─────────────────────┘
```

角色说明（避免术语混乱）：ALVR 里 **PC 端叫 server/streamer（发流）**，头显端叫 client（收流）。你所说的"高配服务端"= ALVR server，"低配客户端"= 本工程。原仓库的 client 是跑在**华为手机上的 APK**；本工程把它改写为跑在**低配 Windows PC 上**。

## 2. 为什么不能直接复用上游源码编译

这是必须先讲清楚的坑（否则你会卡在编译上）：

| 障碍 | 事实 | 本工程对策 |
|---|---|---|
| 华为 OpenXR fork 缺失 | `deps/openxrs-huawei/` 是空目录；作者日志："唯一可用客户端 = 原作者 2026-08-15 的 `.so`（67MB），本机重编不等价（华为 fork 已丢）" | 不使用 `client_openxr`（OpenXR 显示层）；自己用 D3D11 画 SBS |
| wgpu-hal patch 指向缺失目录 | 根 `Cargo.toml`：`[patch.crates-io] wgpu-hal = { path = "deps/wgpu-hal-huawei" }`，目录不存在 → 整个 workspace 无法 configure | 本工程是独立 crate，**不挂进上游 workspace** |
| Windows 侧视频解码是空实现 | `client_core/src/video_decoder/mod.rs`：`#[cfg(not(android))] push_nal → false` | 用 FFmpeg 子进程解码（本工程 `src/decoder.rs`） |
| settings-schema 走 git 依赖 | `alvr_common`/`alvr_session` 依赖 `settings-schema-rs`（git rev），离线不可得 | 协议结构在本工程内自包含重写（`src/protocol.rs`） |

结论：**本工程只用上游的"线协议规格"（已逐字段核对），不编译上游任何 crate。**

## 3. 线协议规格（逐字节，来自上游源码）

### 3.1 发现阶段
- 客户端 UDP 绑定 `0.0.0.0:9943`，开启广播；
- 向 `255.255.255.255:9943` 发 **56 字节**包（`client_core/src/sockets.rs`）：
  - `[0..8]` = ASCII `"ALVR"` + 补零
  - `[16..24]` = `protocol_id_u64()` 小端（版本主号 "20" 的 hash；华为专版放宽版本校验）
  - `[24..]` = 主机名 UTF-8
- 同时在本机 TCP `9943` 监听；server 看到广播后主动连入。

### 3.2 控制通道（TCP 9943）
帧格式（`sockets/src/control_socket.rs::framed_send`）：
```
[u32 payload长度 大端][bincode 序列化的包]
```
握手时序（`client_core/src/connection.rs`）：
1. C→S `ClientConnectionResult::ConnectionAccepted{ client_protocol_id, display_name, server_ip, streaming_capabilities }`
   - 能力集含：`default_view_resolution`、`supported_refresh_rates`（含 70/72）、`microphone_sample_rate`、foveated/HDR/10bit 能力
2. S→C `StreamConfigPacket{ session: JSON, negotiated: JSON }`
   - `negotiated` 是 `NegotiatedStreamingConfig` 的 JSON：`view_resolution/refresh_rate_hint/game_audio_sample_rate/wired/...`
3. S→C `StartStream`（或先 `DecoderConfig{codec,config_buffer}`——SPS/PPS）
4. C 监听另一端口（默认 9944）作为流通道，C→S `ClientControlPacket::StreamReady`
5. S 连入流通道，开始推流

### 3.3 流通道（TCP/UDP，端口由 session 决定）
分片格式（`sockets/src/stream_socket.rs`，共 18 字节前缀）：
```
[u32 负载长度 大端][u16 流ID][u32 包序号][u32 分片总数][u32 分片序号][header bincode][payload]
```
- 流 ID：`0=TRACKING 1=HAPTICS 2=AUDIO 3=VIDEO 4=STATISTICS`
- 视频 header = `VideoPacketHeader{ timestamp: Duration, is_idr: bool }`
  - bincode 的 `Duration` = **u64 秒 + u32 纳秒，小端，共 12 字节**（已实测验证）
- 视频 payload = **Annex B 的 H.264 NAL**（含 `00 00 00 01` 起始码），可直接喂 FFmpeg
- 丢包处理：`is_idr` 重置损坏标志；非 IDR 且检测到丢包 → 发 `RequestIdr`

### 3.4 头姿回传
- `Tracking{ target_timestamp, device_motions: [(device_id, DeviceMotion)], ... }`
- `DeviceMotion{ pose: Pose{orientation xyzw, position xyz}, linear_velocity, angular_velocity }`
- head device id = `0`（上游 `common` 的 head id 约定）
- 本工程只填朝向（3DoF），位置固定原点

## 4. 本工程模块与数据流

| 模块 | 文件 | 职责 |
|---|---|---|
| 协议 | `src/protocol.rs` | 包结构、发现包、控制帧、分片头编解码（含单元测试） |
| 网络 | `src/client.rs` | 发现→握手→收流重组→回传 tracking 的主循环 |
| 解码 | `src/decoder.rs` | H.264 NAL → FFmpeg 子进程 → BGRA 帧 |
| 渲染桥接 | `src/main.rs`(`render` 模块) + `cpp/sink_renderer.cpp` | BGRA 帧 → D3D11 SBS 立体输出到眼镜；IMU → 头姿 |

数据流：
```
NAL(网络) → push_nal → FFmpeg(stdin) → BGRA(stdout) → submit_frame → D3D11 纹理
                                                              ↓
                                                    分眼 UV + 曲面网格 → Present
IMU(HID) → 四元数 → pose_provider() → Tracking → 流通道回传 server
```

## 5. 与"原方案（手机当客户端）"的取舍

| 维度 | 手机 APK（原仓库） | 本工程（低配 PC） |
|---|---|---|
| 显示 | 华为 OpenXR Runtime + HiSilicon 硬解 | D3D11 SBS 输出，FFmpeg 软/硬解 |
| 头姿 | Runtime 6DoF | IMU 3DoF（位置固定） |
| 手柄 | 华为 6DoF Gaming Kit via OpenXR | 未实现（见"已知限制"） |
| 编码侧 | 不变（高配 PC 的 ALVR server） | 不变 |
| 前提 | 手机+眼镜（USB-C 被占） | 眼镜直插低配 PC |

## 6. 已知限制与未验证项（务必阅读）

1. **头姿为 3DoF**：只读 IMU 朝向，无位置追踪；快速头部平移不会反映到画面。这是华为 SLAM 私有的直接后果。
2. **手柄输入未实现**：需要把 6DoF 手柄按键/姿态映射成 ALVR 的 `Buttons`/`ActiveInteractionProfile` 控制包；本版聚焦"画面能看"。
3. **Windows 侧解码用 FFmpeg 软解为主**：该接收端环境若用 AMD Valve OEM 驱动，硬件媒体引擎不可用（作者日志实测），软解是稳妥选择；有 NVENC/NVENC Decode 的机器可换硬解。
4. **协议细节以 v20.14.1 为准**：如果高配 PC 的 ALVR 版本不同，字段可能变化；`protocol_id` 已放宽校验，但真实反序列化失败会拒绝。建议两端同版本。
5. **本工程的 Rust 代码已在本机通过 `cargo test`（协议单测）**；但 Windows 渲染/C ABI 部分无法在无硬件的沙箱验证，需按 `02-构建与运行.md` 在你自己的 Windows + 真机眼镜上编译验证。
6. **时间戳同步简化**：`Tracking.target_timestamp` 当前填 0；正式低延迟需与 server 做时钟同步（见 `03-接线与调优.md`）。
